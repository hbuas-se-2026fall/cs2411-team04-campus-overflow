# 统一语言（Ubiquitous Language）

> 代码命名、Issue 标题、PR 描述、站会发言统一使用本表术语。
> **来源**：`CampusOverflow-实验指导书V3.pdf` 3.3 节 + 仓库代码 javadoc（2026-11-09 逐一核对，非自行编写）。
> 修改本表请走 PR；新增术语必须同时给出代码落点。

## 1. Q&A 上下文（`co-qa`）

| 术语 | 代码名 | 一句话定义 |
| --- | --- | --- |
| 问题 | `Question` | 学生针对某门课程发起的提问，含标题（`Title`）、Markdown 正文（`MarkdownBody`）与标签（`Tags`），可被回答、投票、评论、采纳。 |
| 回答 | `Answer` | 针对某个问题提交的回复，可被投票、采纳、教师认证；被采纳后回答者本人不能删除。 |
| 采纳 | `Question.accept` | 提问者或课程管理者把某条回答标记为最佳答案，一题只能有一个；被采纳的回答须属于本题（`QA-1010`）且未被删除（`QA-1011`）。 |
| 教师认证 | `Answer.endorse` | 课程教师/助教给优质回答打上认证标记，非课程管理者调用报 `QA-3004`；会触发「名师认可」徽章与声誉事件。 |
| 投票 | `Vote` | 同一用户对同一内容（问题或回答）只能有一票，取值 +1 / −1；改投按「新效果 − 旧效果」增量记分，撤销即删除。 |
| 评论 | `Comment` | 挂在问题或回答下的短回复，支持一层「二级回复」，正文可 @昵称。 |
| 软删除 | `Question.softDelete` / `Answer.softDelete` | 只打删除标记、保留数据行；课程管理者可删除任意内容，提问者只能删除「尚无回答」的问题，否则报 `QA-1013`。 |
| 已删除保护 | `QA-1020` | 已软删除的内容不能再被编辑、回答、采纳、认证或删除。 |

## 2. 声誉上下文（`co-reputation`）

| 术语 | 代码名 | 一句话定义 |
| --- | --- | --- |
| 声誉 | `ReputationAccount` | 用户在本上下文累计的信誉分与等级；只能由账本流水累加，不允许直接改分。 |
| 账本流水 | `LedgerEntry` | 只追加的声誉变动记录，唯一键 `(eventId, userId, reason)`，使事件重复投递天然幂等（ADR-004）。 |
| 每日上限 | `ReputationRulebook.applyDailyCap` | 反作弊规则：每人每个自然日（**按北京时间 `Asia/Shanghai`**）因被投票获得的正向声誉最多 +200。 |
| 悬赏 | `Bounty` | 提问者为吸引回答挂出的声誉赏金；`OPEN → AWARDED`（被采纳）或 `OPEN → EXPIRED`（到期），终态不可变。 |
| 徽章 | `BadgeAward` / `BadgeType` / `BadgePolicy` | 按规则一次性授予的成就标记，共 6 种：初来乍到（提交首个回答）、初露锋芒（首个回答被采纳）、解惑达人（累计 10 个回答被采纳）、名师认可（回答获教师认证）、小有名气（声誉达 100）、德高望重（声誉达 1000）。 |
| 排行榜 | `LeaderboardService` / `LeaderboardPeriod` / `LeaderboardEntryView` | 按周期（`WEEK` / `MONTH` / `TERM` / `ALL`）对声誉排名的只读视图，条目为 `(rank, userId, displayName, verified, score)`。 |
| 对账 | `ReconciliationService` | 适应度函数 FF-8：校验每个账户的声誉**等于**其流水之和，不等即说明有漏记或错记。 |

## 3. 发现上下文（`co-discovery`）

| 术语 | 代码名 | 一句话定义 |
| --- | --- | --- |
| 搜索投影 | `SearchDocument` / `SearchIndexProjector` | 由事件投影出的「如何被找到」读模型，与问题聚合是两个模型（CQRS）。 |
| 相关问题 | `RelatedQuestionPolicy` | 按标签集合的 Jaccard 相似度排序推荐（`J(A,B)=|A∩B|/|A∪B|`）；相似度相同时得分高、已采纳者优先。 |
| 提及 | `MentionParser` | 从评论中解析 @昵称（2–20 字符，不含空格与 @），每条评论最多提醒 5 人，防止滥用。 |
| 通知 | `Notification` / `NotificationType` | 站内提醒，类型含 `ANSWER_RECEIVED`、`ANSWER_ACCEPTED`、`ANSWER_ENDORSED`、`MENTIONED`、`BOUNTY_AWARDED`；同一 `(sourceEventId, recipientId)` 只发一次。 |

## 4. 身份与平台

| 术语 | 代码名 | 一句话定义 |
| --- | --- | --- |
| 课程 | `Course` | 问答的组织单位（`code + term` 唯一），问题都挂在某门课程下。 |
| 课程角色 | `CourseRole` | 课程内身份：`STUDENT` / `TA` / `TEACHER`，决定能否认证、采纳、删除他人内容。 |
| 校园身份认证 | `AdminUserService.verify` / `User.verified` | 学院管理员认证用户的真实身份，通过后显示认证徽章；与「教师认证回答」是两件事。 |
| 事务性发件箱 | `outbox_event` / `OutboxRelay` | 写操作在同一事务内把事件写入 outbox 表，由中继按 id 顺序投递，保证「存储成功即事件必达」。 |

## 5. 两个容易混淆的「认证」

| 概念 | 代码落点 | 含义 | 错误码 |
| --- | --- | --- | --- |
| 教师认证 | `Answer.endorse` | 课程教师/助教给**回答**打优质标记 | 非课程管理者：`QA-3004` |
| 校园身份认证 | `AdminUserService.verify` / `User.verified` | 学院管理员认证**用户身份** | — |

> Sprint 2 会同时出现这两件事，命名时请勿混用：说「认证」时请明确是「认证回答」还是「认证用户」。

## 6. 与代码注释不一致、但有意为之的一处

**每日上限的时区**：本表写「北京时间（`Asia/Shanghai`）」，而 `ReputationRulebook` 的 javadoc 目前写的是「UTC」。

- 理由 1：`AcademicTerm.CAMPUS_ZONE` 已是 `Asia/Shanghai`，排行榜的周/月/学期周期按北京时间切分；上限若按 UTC 算，同一人的「今天」在排行榜上会算成「昨天」，两套时区迟早出 bug。
- 理由 2：校园系统用户全在国内，按 UTC 会让北京时间早上 8 点前的投票被计入前一天，用户会觉得「怎么没加分」。
- 处理：`ReputationRulebook.applyDailyCap` 目前仍是 `TODO(S3)` 未实现，实现时统一按 `CAMPUS_ZONE`，并同步修掉 javadoc 里的 UTC 表述。
