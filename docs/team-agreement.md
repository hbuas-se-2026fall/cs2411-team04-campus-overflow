# 团队约定

> 建立于 2026-11-06。修改走 PR。
> 配套：`docs/status.md`（进度总览）、`docs/progress/`（个人进度）、`AGENTS.md`（给 AI 与人的统一约定）。

## 1. 角色

| 角色 | 人 | 负责 |
| --- | --- | --- |
| PO + SM | Bugmageddon | 看板、任务分配、评审、演示与答辩 |
| 技术负责人 | 代一鸣（qwerbnmv） | Q&A 与 Reputation 核心领域，技术兜底 |

## 2. 节奏

| 事件 | 时间 | 时长 |
| --- | --- | --- |
| 站会 | 每周一、三、五，群里三问 | 15 分钟 |
| 计划会 | 每批次开始 | 30 分钟 |
| 评审 | 每批次结束 | 30 分钟 |
| 回顾 | 评审之后 | 20 分钟 |

## 3. 工作方式

- **每人同时只做 1 个任务**，完成后自己去 `Ready` 列拉下一个。
- 看板四列：`Ready → 进行中 → 待评审 → 完成`。
- 分支：`feat/xxx`、`fix/xxx`、`docs/xxx`、`ci/xxx`；一个任务一个分支，生命周期 ≤3 天。
- 提交：`<type>(<scope>): 中文简述`。
- PR：≤400 行，关联 Issue，附测试证据。
- **PR 必须关联至少 1 个 Issue**：正文写 `Closes #号`，合并后由 GitHub 自动关闭该 Issue。
  没有关联 Issue 的 PR 不予合并；唯一例外是 `hotfix`，且必须在 PR 中说明原因。
- **禁止手动关闭"已完成"的 Issue**：只能由 PR 合并自动关闭。
  允许手动关闭的只有三种情况：范围裁剪、重复、超时取消，且必须在评论里写明原因。
  这样做是为了让「Issue 状态」与「代码是否真的合并」永远一致。

## 4. 评审归属

| 改动范围 | 谁可以批 |
| --- | --- |
| `co-qa/` | 代一鸣、PO |
| `co-reputation/` | **PO 必须参与**，代一鸣可批 |
| `co-discovery/`、`frontend/` | 谢守航、PO |
| 共享内核、`.github/`、CI、发布 PR | **必须 PO** |

**24 小时规则**：PR 开了 24 小时没人批，作者直接找上表对应的人批，不必等 PO。
**例外**：涉及共享内核、CI、发布 PR 的，必须 PO 批。

## 5. 就绪定义（DoR）

一个任务可以开始做，必须满足：

- [ ] 有指派的负责人
- [ ] 有可验证的验收标准（3 条以内）
- [ ] 已标注涉及的文件或方法
- [ ] 依赖已就绪（否则标 `status:blocked`）

## 6. 完成定义（DoD）

一个任务算完成，必须全部满足：

- [ ] 代码经 PR 合入 `develop`，至少 1 名非作者 Approve
- [ ] 相关测试全绿，**未修改任何已有断言**
- [ ] `ArchitectureTest` 通过
- [ ] PR 的 Checks 全绿
- [ ] 已更新本人 `docs/progress/<用户名>.md`
- [ ] 涉及接口或界面时，附调用截图

## 7. 进度更新

- `docs/status.md`：**只有 PO 改**。
- `docs/progress/<用户名>.md`：本人改，别人不许动。
- 代码类 PR 若未更新本人进度文件，CI「进度文件检查」会失败。

## 8. 红线

- 不修改已有测试断言、不删除测试、不加 `@Disabled`。
- 不绕过 PR 直接推送 `main` / `develop`。
- 不提交密钥、真实学号、手机号。
- 不手动关闭「已完成」任务的 Issue（见 §3，只能由 PR 合并自动关闭）。
- 使用 AI 辅助需在 PR 描述中注明。

## 9. 范围纪律

- 每批次只做 `Ready` 列里的卡；不在列里的想法先建成 `Could` 卡片，不当场开工。
- 批次门禁未通过前，不开下一批。
