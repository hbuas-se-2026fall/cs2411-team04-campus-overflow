| Sprint 4 | 第 8 周 | 发布 | 「稳定化、体验打磨、可观测，完成 v1.0 发布」 | v1.0.0 |

- V2（p.4, §1.3）：`开发周期： 8 周（ 1 个启动 Sprint + 3 个开发 Sprint + 1 个发布 Sprint ）`

## 5. 团队组织、角色分工、Scrum 事件、DoR/DoD、估算与容量

### 5.1 Scrum 角色（4.1 节 p.20）

**产品负责人（PO）——本比对中最重要的一处变化：**

- **V2（p.20）**：由「团队的产品经理（建议成员 B）」担任；职责包括「维护 Product Backlog 排序、编写验收标准、在评审会上代表团队接受/拒绝 PBI」以及「在本地 IntelliJ 导入起始代码并**创建团队仓库（PO 个人账号下）**，邀请成员为协作者，配置分支保护与看板。**本项目不另设仓库管理员**」。
- **V3（p.20）**：任课教师「作为主要干系人（客户），**同时是 GitHub 组织的所有者**」；PO 职责改为「在本地 IntelliJ 导入起始代码并**推送到教师为本组创建的私有仓库**，**作为本组仓库的管理员（Admin）**配置分支保护与看板」。
- **差异结论**：PO 从"仓库所有者 + 建库人"降为"本组仓库 Admin + 被授权人"，仓库所有权上移到教师；"不另设仓库管理员"的表述被删除。

**Scrum Master（SM）与开发者（两版逐字相同）：**

- SM：「组内成员，**每个 Sprint 轮换**」；职责「主持各项 Scrum 事件、维护看板与燃尽图、清除障碍（环境、冲突、CI 红灯）、监督工作约定」。
- Developers：「全体成员（含 PO 与 SM）」，要求「**每人每个开发 Sprint 至少交付 1 个领域层 PR 与 1 个应用层 PR**」。
- **差异结论**：SM 轮换制与"每人每 Sprint 两个 PR"的硬性要求两版一致，未放宽。

### 5.4 Scrum 事件与时间盒（4.2 节 p.20–21）——逐字相同

- Sprint 计划会：「每个 Sprint 第 1 天（实验课）」，「2 周 Sprint ≤ 2 h；1 周 Sprint ≤ 1 h」，输出「Sprint Goal + Sprint Backlog（任务拆到 ≤ 1 天）」。
- 每日站会：「每周至少 3 次」，「15 min」，三问「昨天完成了什么？今天计划做什么？遇到什么阻碍？」。
- Backlog 精化：「每个 Sprint 中段」，「≤ 1 h」，产出「达到 DoR」。
- Sprint 评审会：「Sprint 最后 1 天（实验课，教师参加）」，「≤ 1 h（每组 15–20 min 演示）」。
- Sprint 回顾会：「评审会之后」，「≤ 45 min」，产出「1～3 条可执行改进项」。
- **差异结论**：事件、时间点、时间盒与输入输出两版一致。

### 5.5 Scrum 工件载体（4.3 节 p.21）——逐字相同

- Product Backlog = 「GitHub Projects（Board/Table 视图）中所有带 `type:story` 的 Issue」，字段「Priority、Story Points、Sprint」，「PO 负责排序」。
- Sprint Backlog = 「当前 Milestone（如 Sprint 1）中的 Story Issue + 拆出的 Task Issue」，「Sprint Goal 写在 Milestone 描述中」。
- Increment = 「main 分支上的版本标签（v0.1.0 … v1.0.0）+ GitHub Release + CI 构建的镜像」。
- 燃尽图 = 「Projects 的 Insights（按 Story Points 统计）」，「SM 每次站会后更新」。
- **差异结论**：载体与维护规则不变；但 7.4 节把看板的归属从"PO 个人账号下"改为"组织下"（见 §7.2）。

### 5.6 DoR / DoD（4.4 节 p.21–22）——逐字相同

- **DoR**：①「以"作为…我希望…以便…"格式书写」并关联史诗与上下文标签；②「有可验证的验收标准（Given/When/Then）」并标出对应测试；③「已估算故事点（≤ 8 点；超过则拆分）」、依赖已识别。
