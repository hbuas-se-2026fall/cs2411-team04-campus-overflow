# ADR-009 渐进式质量门禁

- 状态：已接受
- 日期：2026-11-06
- 决策人：PO（Bugmageddon）
- 相关：`.github/workflows/ci.yml`、ADR-001、指导书 8.2 / 8.3 节

## 背景

起始代码里 Q&A / Reputation / Discovery 三个上下文共有 **107 个待实现方法**，对应约 **38 个失败的测试**。这是有意的设计——测试即需求说明书。

但 CI 流水线默认要跑**全部模块**的单元测试与集成测试。结果是：

1. `develop` 从第一天起持续红灯，每个 PR 都挂红叉；
2. 队友无法从"红灯"判断是自己写坏了还是本来就没实现，排障成本高；
3. 分支保护无法启用"必须通过状态检查"——因为永远没有一次全绿，这个门禁等于永久失效；
4. 若为了合并而关闭检查，就彻底失去了 CI 的意义。

## 决策

**按 Sprint 范围逐步扩大必须通过的测试集合**，而不是一次性要求全绿。

1. `ci.yml` 顶部引入变量 `SPRINT_MODULES`，列出当前 Sprint 必须全绿的模块（Maven `-pl` 语法）。
2. 单元测试、覆盖率门禁两步只在该范围内执行（`-pl "$SPRINT_MODULES" -am`）。
3. 编译与 ArchUnit 架构检查**始终对全量模块执行**——骨架必须永远可编译、架构约束必须永远成立。
4. 集成测试在 S0–S2 使用 `continue-on-error: true`（允许失败），S3 起删除该行改为硬门禁。
5. 镜像构建只在推送到 `main` 时执行；同一分支的新推送会取消仍在运行的旧流水线（`concurrency`）。

当前（S0）范围：

```
SPRINT_MODULES = co-shared-kernel,co-identity/co-identity-domain
```

演进计划：

| Sprint | 追加模块 |
| --- | --- |
| S1 | `co-qa/co-qa-domain`、`co-qa/co-qa-application` |
| S2 | `co-reputation/co-reputation-domain`、`co-reputation/co-reputation-application` |
| S3 | 删除该变量，恢复全量 `mvn test` / `mvn verify` |

## 后果

**正面**

- `develop` 与 `main` 保持绿色，红灯重新具备信号价值；
- 可以安全地启用"必须通过状态检查"的分支保护；
- 每完成一个上下文就扩大范围，质量门禁随进度收紧；
- 节省 Actions 分钟（组织每月仅 3000 分钟，全组共享）。

**负面 / 代价**

- 未纳入范围的模块，其失败在 CI 上不可见，只能靠本地 `mvn test` 与代码评审兜底；
- 每次 Sprint 计划会后需有人记得更新 `SPRINT_MODULES`，否则门禁会滞后。

**约束（红线）**

- 渐进式门禁**只能缩小运行范围**，不得通过 `-Dmaven.test.failure.ignore=true`、`@Disabled`、删除测试或修改断言来"变绿"。
- 任何对 `ci.yml` 的修改都必须走 PR；教师可检查该文件的提交历史。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 保持全量测试，接受长期红灯 | 红灯失去信号价值，且无法启用状态检查保护 |
| 关闭 CI，靠人工评审 | 失去自动化质量保障，答辩无法展示流水线 |
| 用 `-Dmaven.test.failure.ignore=true` 让任务"通过" | 属于掩盖问题，触碰课程红线 |
| 先删掉失败测试，实现后再加回 | 等同于篡改需求，触碰学术诚信红线 |
| 只跑 `mvn compile`，不跑测试 | 门禁形同虚设，无法在 Sprint 内及时发现回归 |
