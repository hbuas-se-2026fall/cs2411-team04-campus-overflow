# ADR-006：问题与回答软删除，投票撤销即删除

**状态**：已接受 ｜ **驱动特征**：可审计性、可追溯 ｜ **相关场景**：QS-03

## 背景
用户内容被删除后，声誉账本仍要能解释"这 15 分是怎么来的"。若物理删除，`rep_ledger` 里的内容 id
会指向不存在的行，对账（FF-8）与答辩演示都无法自证。另一方面，评论与投票不进入账本摘要，
删除它们没有追溯需求。

## 决策
**问题与回答软删除；评论当前没有删除路径；投票撤销即物理删除。**

- `deleted_at` 只有 **2 个字段**，都在
  `backend/co-qa/co-qa-infrastructure/src/main/resources/db/migration/qa/V202609010200__qa_init.sql`：
  `qa_question.deleted_at`（第 14 行）、`qa_answer.deleted_at`（第 45 行）。
  同文件第 17、18、48 行也出现 `deleted_at`，但那是**索引列**，不是字段。
- 领域实现：`Question.softDelete(...)`
  （`backend/co-qa/co-qa-domain/src/main/java/com/campusoverflow/qa/domain/Question.java:114`）与
  `Answer.softDelete(...)`（同目录 `Answer.java:75`）。
- 硬约束：已软删除的内容不能再编辑、回答、采纳、认证或删除，统一抛 `QA-1020`
  （`Question.java:134`、`Answer.java:89`）。
- 读路径过滤：`backend/co-qa/co-qa-infrastructure/src/main/java/com/campusoverflow/qa/infrastructure/query/JdbcQaReadModel.java`
  第 42、55、64 行的查询都带 `deleted_at IS NULL`。
- 评论：`qa_comment` 表无 `deleted_at`，`CommentRepository` 只有查询与保存，**当前没有删除入口**。
- 投票：`qa_vote` 无 `deleted_at`，撤销是**物理删除**（`VoteRepository.delete`，
  以及 `backend/co-qa/co-qa-domain/src/main/java/com/campusoverflow/qa/domain/Vote.java:7` 的注释「撤销即删除」）。

## 后果
- 正面：声誉可对账、内容可恢复、审计链路完整。
- 负面：所有查询都必须记得带 `deleted_at IS NULL`，漏一处就会把已删内容展示出来；
  表只增不减，长期需要归档。
- 重新考虑的条件：要做"回收站 / 恢复"时，软删除正好是基础；若某类内容确定不需追溯，可单独物理删除。

## 被否决的替代方案
- **物理删除 + 归档表**：多一套同步逻辑，归档表与主表容易不一致。
- **全部物理删除**：账本无法解释来源，对账会失败。
