# ADR-010：悬赏积分与声誉是两种独立货币

**状态**：已接受 ｜ **驱动特征**：可解释性、激励设计 ｜ **相关场景**：QS-06、R-3

## 背景
同一个用户身上会出现两个数字：**声誉**（提问、回答、被投票、被采纳累积出来的荣誉值）与
**悬赏积分**（用来发悬赏、可消耗的货币）。它们很容易被当成"一种东西的两种叫法"，
于是出现两类错误设计：

- 把两者合并成一个数值：发悬赏就会掉声誉，学生会不敢提问；
- 把积分也记进声誉账本：`rep_ledger` 里混入货币语义，「声誉 = 流水之和」的对账口径随之崩掉。

## 决策
`rep_account` 上同时保留两组字段，**互不换算、互不影响**：

| 字段 | 含义 | 变动来源 |
| --- | --- | --- |
| `reputation` | 荣誉值 | **只能是账本流水之和**（`rep_ledger`） |
| `available_points` | 可用悬赏积分 | 开户发放、悬赏冻结/退回 |
| `frozen_points` | 冻结中的悬赏积分 | 发起悬赏冻结、结算或到期解冻 |

代码落点：

- 表结构：`backend/co-reputation/co-reputation-infrastructure/src/main/resources/db/migration/reputation/V202609010300__reputation_init.sql:2`（`rep_account`）。
- 声誉只能经账本改变：`ReputationAccount.applyReputation(int)`
  （`backend/co-reputation/co-reputation-domain/src/main/java/com/campusoverflow/reputation/domain/ReputationAccount.java:42`），
  且**不做下限截断** —— 截断会破坏对账不变量 FF-8。
- 积分是独立钱包：开户 `ReputationAccount.open`（`ReputationAccount.java:29`）按角色发放
  （`ReputationRulebook.initialPoints`，`ReputationRulebook.java:50-56`：教师/管理员 1000、助教 500、学生 0）；
  `freezePoints`（`:47`）、`spendFrozen`（`:57`）、`refundFrozen`（`:64`）三个方法只在钱包内部流转。
- 悬赏流程（`BountyService.java`）：`open`（`:56`，第 67 行 `freezePoints`）→ 采纳时 `settleOnAccept`
  （`:79`，第 93 行 `spendFrozen`）→ 到期 `expireDue`（`:106`，`refundFrozen`）。
- **获奖者拿的是声誉，不是积分**：`BountyService.settleOnAccept` 第 96–97 行给获奖者记一条
  `BOUNTY_AWARDED` 流水，金额等于悬赏分；发起人的冻结分直接消失（不转账给获奖者）。
- 悬赏边界：`Bounty.java:15-17`（`MIN_POINTS = 10`、`MAX_POINTS = 500`、`MAX_DAYS = 14`），
  状态机 `OPEN → AWARDED / EXPIRED`（`Bounty.award:72`、`Bounty.close:84`）。

### 为什么学生不能发起悬赏（设计如此，不是缺陷）

开户积分按指导书第 36 页的建议值实现：**教师 / 管理员 1000、助教 500、学生 0**
（`ReputationRulebook.initialPoints`，`ReputationRulebook.java:50-56`）。学生发起不了悬赏，
是因为同时存在两道**互相独立**的锁：

1. **积分锁**：`ReputationAccount.availablePoints` 的全部写入点只有三处 ——
   构造函数/`open()`（`ReputationAccount.java:20`、`:29`，学生初始值与 0 等同）、
   `freezePoints()` 扣减（`:47`，第 52 行）、`refundFrozen()` 退回（`:64`，第 68 行，前提是**先冻结过**）。
   **没有任何加分入口**，所以学生余额恒为 0；而发起悬赏的下限是 `Bounty.MIN_POINTS = 10`。
2. **权限锁**：`Bounty.open(...)` 的领域规则是「仅课程管理者可发起」，否则抛 `REP-3001`
   （`Bounty.java:49-51`）；测试 `BountyAndAccountTest:22` 用学生 Actor 断言 `ForbiddenException`。

结论：**悬赏是课程管理者的运营功能，不是学生自助功能**。演示脚本里「发起悬赏」排在教师认证之后、
用教师身份执行，正是这个原因；即使给某个学生手工加到 10 分以上，他仍会被权限锁挡下（`REP-3001`）。

## 后果
- 正面：两个数字语义清晰 ——「声誉高但没积分」与「积分花光但声誉不变」都是合法状态；
  声誉可对账（FF-8），积分可退回（悬赏到期不损失）。
- 负面：界面上必须**分开显示**两个数字并解释差异，否则用户会以为积分花掉掉了声誉；
  积分没有账本，只有 `audit_log` 的 `BOUNTY_OPEN` 记录，追溯能力弱于声誉。
- **学生无法发起悬赏**（0 积分 + 非课程管理者，双重限制）：这是设计取舍 ——
  悬赏是教师/助教针对具体问题「买一个答案」的运营手段，若开放给学生，
  会出现「互相发悬赏抬声誉」的刷分路径，而声誉本身又参与排行榜与徽章。
- 重新考虑的条件：如果以后要支持「充值/购买积分」，必须补一套积分账本（否则无法审计）。

## 被否决的替代方案
- **单一数值**（声誉即积分）：发悬赏会扣声誉，直接打击提问意愿；且声誉不再可对账。
- **把积分记进 `rep_ledger`**：会让「账户声誉 = 流水之和」这个不变量混入货币收支，
  对账任务（`ReconciliationService`、FF-8）将无法判断真伪，等于放弃可审计性。
- **获奖者直接收积分**：等于系统凭空增发货币（发起人的分是"花掉"而不是"转出"），
  积分总量会失真。
