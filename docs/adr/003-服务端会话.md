# ADR-003：认证采用 Redis 服务端会话而非 JWT

**状态**：已接受 ｜ **驱动特征**：可运维性、可撤销性 ｜ **相关场景**：QS-02

## 背景
校园系统里角色会变：学生被管理员认证（`AdminUserService.verify`）、课程内被任命助教、账号被封禁。
若用 JWT，令牌签发后在过期前一直有效，上述变更最长要等一个过期周期才生效，
"强制下线"还得额外维护黑名单。

## 决策
采用 **Spring Session + Redis 的服务端会话**，浏览器只持有一个 `SESSION` Cookie。

- 依赖：`backend/co-bootstrap/pom.xml` 引入 `spring-session-data-redis`。
- 会话参数：`backend/co-bootstrap/src/main/resources/application.yml` 中
  `spring.session.timeout: 30m`、`spring.session.redis.namespace: co:session`；
  同文件 `server.servlet.session.cookie` 定义 Cookie 名为 `SESSION`、`HttpOnly`、`SameSite=Lax`。
- 安全装配：`backend/co-bootstrap/src/main/java/com/campusoverflow/bootstrap/security/SecurityConfig.java`
  （类注释即标注 ADR-003），用 `HttpSessionSecurityContextRepository` +
  `RequestAttributeSecurityContextRepository` 组合保存安全上下文；`formLogin` / `httpBasic` 关闭，
  登录走 `AuthController`。
- 用户身份：`backend/co-identity/co-identity-infrastructure/src/main/java/com/campusoverflow/identity/infrastructure/security/SecurityUser.java`
  实现 `UserDetails`，由同目录的 `DbUserDetailsService` 装配；
  密码编码器在 `IdentitySecurityBeans.java`（BCrypt，cost=10）。

## 后果
- 正面：角色变更、封禁**立即生效**（删会话即可）；令牌不落在浏览器可读位置，XSS 拿不到凭据；
  服务端会话天然支持在线人数统计与单点登录。
- 负面：每个请求多一次 Redis 查询；Redis 成为登录链路单点，挂掉就无法登录；
  水平扩容依赖共享 Redis（本项目本来就有）。
- 重新考虑的条件：要开放第三方 API（无 Cookie 场景）时，可另加一套短期令牌，但不必替换会话机制。

## 被否决的替代方案
- **JWT 无状态**：撤销要黑名单，黑名单又要查 Redis，等于把状态加回来，还多出密钥轮换与时钟偏差问题。
- **JWT + 短过期**：角色变更最长延迟一个过期周期，教师认证、封禁场景不可接受。
