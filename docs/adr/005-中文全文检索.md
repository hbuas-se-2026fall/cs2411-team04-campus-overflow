# ADR-005：搜索使用 MySQL ngram 全文索引

**状态**：已接受（可演进） ｜ **驱动特征**：可部署性、成本 ｜ **相关场景**：QS-05

## 背景
校园问答需要中文搜索。MySQL 默认全文索引按空格分词，中文整句会被当成一个词，几乎搜不到；
引入 Elasticsearch 则要多一个中间件、一份索引运维，4 人团队在课程环境里装不下。

## 决策
用 MySQL 8 的 **ngram 全文索引**做搜索，数据来自事件投影出的读模型。

- 建表与索引：`backend/co-discovery/co-discovery-infrastructure/src/main/resources/db/migration/discovery/V202609010400__discovery_init.sql`
  第 25 行 `FULLTEXT KEY ft_doc (title, body_text) WITH PARSER ngram`。
- 分词参数：`deploy/docker-compose.yml` 第 12–13 行 `--ngram-token-size=2`、
  `--innodb-ft-enable-stopword=0`；后者是因为默认停用词含 `a`、`i` 等，会让含这些字母的
  ngram 词元被丢弃（该 SQL 文件第 1–3 行的注释已说明）。
- 写入路径唯一：`backend/co-discovery/co-discovery-application/src/main/java/com/campusoverflow/discovery/application/SearchIndexProjector.java`
  消费集成事件写入 `dis_search_doc`；查询侧经 domain 层的 `SearchPort` 抽象访问。
- 自建 MySQL 必须手动设置同样两个参数，否则中文搜索查不出结果。

## 后果
- 正面：零新增中间件，部署面只有 MySQL + Redis；索引与业务数据同库，便于一致性排查。
- 负面：ngram 索引体积大、写入比普通索引慢；相关性排序能力弱于专用检索引擎，
  本项目用标签匹配与时间先后兜底；迁移数据库时这两个启动参数要一起搬。
- "可演进"的含义：写入只经 `SearchIndexProjector`，查询只经 `SearchPort`，
  将来换检索引擎时改动集中在这两处。

## 被否决的替代方案
- **Elasticsearch**：多一个中间件与一套运维，课程环境与 4 人团队不划算。
- **`LIKE '%关键词%'`**：无法使用索引，数据量上来后退化为全表扫描。
