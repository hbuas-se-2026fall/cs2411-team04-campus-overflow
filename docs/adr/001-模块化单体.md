# ADR-001：采用模块化单体 + 六边形分层

**状态**：已接受 ｜ **驱动特征**：可演进性、可测试性 ｜ **相关场景**：QS-01、R-1

## 背景
课程项目要在一个学期内由 4 人完成 4 个限界上下文（Identity / Q&A / Reputation / Discovery）。
若拆成微服务，注册中心、配置中心、分布式事务与部署运维会把工期吃掉大半；若只做单模块分层，
包之间的依赖全靠自觉，几周后必然出现 domain 直接 import Spring、上下文互相 import 实现类的情况，
测试也无法脱离框架运行。

## 决策
后端是**模块化单体**：一个 Spring Boot 进程，用 Maven 多模块强约束边界。

- 4 个限界上下文各 6 个模块（上下文父 POM + `domain` / `application` / `infrastructure` / `interfaces` / `api` 五层），
  加上共享内核、启动装配与父 POM，Maven 反应堆共 **27 个模块**。
- `domain` 层零框架依赖：`backend/co-qa/co-qa-domain/pom.xml` 的依赖只有 `co-shared-kernel`
  与测试库（junit / assertj / jacoco），**没有** Spring / JPA / Jackson。
- 边界由 ArchUnit 守护：`backend/co-bootstrap/src/test/java/com/campusoverflow/architecture/ArchitectureTest.java`
  共 **8 个 `@ArchTest`**，覆盖 FF-1（领域纯 Java）、FF-2（跨上下文只经 api）、FF-3（上下文无环）、
  FF-4（依赖由外向内）、FF-5（api 包轻量）、FF-6（表前缀隔离），另 2 条按上下文参数化。
- 进程内集成走事务性发件箱（见 ADR-002），不做跨进程调用。

## 后果
- 正面：一条 `mvn test` 就能跑完整链路；模块依赖在**编译期**报错，比口头约定可靠；
  将来真要拆服务时，`api` 包与集成事件已经是天然边界。
- 负面：所有模块共享一个 JVM 与一个数据库，无法独立扩缩容；一个上下文的内存泄漏会影响全部；
  模块数多，首次全量构建较慢。
- 重新考虑的条件：需要独立扩缩容，或团队扩大到多组并行修改同一上下文时。

## 被否决的替代方案
- **单模块分层**（一个模块内按 package 划分）：边界靠自觉，除 ArchUnit 外没有编译期保护，最容易腐化。
- **微服务**：4 人 / 4 周的容量下，分布式事务与运维成本远超收益。
